# **katashiro（形代）全体要件・手順・アーキテクチャ仕様 v2**

# **1\. プロジェクト概要**

## **基本情報**

* **ツール名 / リポジトリ名**: `katashiro`（形代：人の身代わりとなるテスト用ダミー個人データ生成ツール）  
* **目的**: 日本のWebサービス・業務システム（決済・KYC・会員管理・バッチ処理）のテスト向けに、最大100万件の重複なし・整合性のあるダミー個人データをミリ秒単位で高速払い出しするGo製シングルバイナリツール。  
* **コアコンセプト**: 「マスタ辞書（内蔵シード。実データの住所約12万件・姓名約1.3万件は利用者が `master fetch` で取得）だけを持ち、100万件の個人データは実行時に \$O(1)\$ で決定論的にオンザフライ合成する」。テストごとに2,000件生成してDBごと使い捨てる運用でも、100万件の一括ロードでも同一アルゴリズムで重複ゼロと完全な再現性を保証する。

## **README記載方針（短縮エイリアス案内）**

* 公式コマンド名は `katashiro` とし、環境競合（`.kts` スクリプトや他コマンドとの衝突）を避けるため、バイナリ側での強制的な短縮名の提供は行わない。  
* READMEの Installation および Quick Start セクションに以下のシェル設定案内を明記する。

```
# Tips: エイリアス設定 (~/.zshrc や ~/.bashrc 等に追加)
alias kata=katashiro
```

# **2\. ビルド・利用手順（ゼロパース起動アーキテクチャ）**

外部マスタデータ（日本郵便CSV・人名辞書）の扱いについては、**開発者（ビルド時）の2ステップ構造**と、**利用者（実行時）の1ステップ完結構造**を両立する。  
さらにv2では、CLI起動時のJSONデシリアライズ遅延（150〜300ms）を完全に排除するため、\*\*オフセットインデックス付きバイナリ（KTS1 形式）\*\*を //go:embed で埋め込み、起動時間1ms未満・ゼロアロケーション参照を実現する。

## **パターンA: 利用者向け（1ステップ完結・推奨）**

ビルド済みバイナリには `//go:embed` 機構によりインデックス化済みの内蔵シード辞書（`addresses.bin`, `names.bin`。47都道府県の代表住所約440件・姓名約350件）が埋め込まれている。利用者は外部依存なしで、インストール直後から即座にデータを生成できる。住所・姓名のバリエーションが必要な場合はパターンCで実データ辞書を取得する。

```
# 例: 重複なしで10件の個人データをJSON出力
katashiro next 10 --format=json

# 例: テストスイート用に2,000件を決定論的に生成してDB投入用に使う
katashiro export 2000 --seed=42 --base-date=2026-01-01 --format=jsonl
```

## **パターンB: 開発者・マスタ更新時（2ステップ構成）**

1. **Step 1（前準備 / マスタ生成）**:  
   `go generate ./...`（`cmd/genmaster`）を実行。内蔵シード（47都道府県の代表住所と姓名）から、または開発時の確認用に日本郵便の `utf_ken_all.zip` および OSS人名辞書（`willnet/gimei` の `names.yml` 等）を取得・クレンジングし、`internal/master/data/` 配下へ固定長オフセット配列＋文字列プールのバイナリ（および確認用JSON）を出力する。  
2. **Step 2（本体ビルド）**:  
   `go build ./cmd/katashiro` を実行。生成されたバイナリ辞書が埋め込まれ、単一バイナリが生成される。

※ 埋め込み辞書は内蔵シードとし、実データ（郵便番号データ・gimei）はリポジトリにもリリースバイナリにも含めない。毎月の郵便番号データ更新のたびにバイナリをコミットする運用を避けるため。

## **パターンC: 利用者による実データ辞書の取得・共有**

1. `katashiro master fetch --out=<DIR>` で日本郵便の郵便番号データと gimei の人名データを取得し、`cmd/genmaster` と共通の処理（`internal/masterbuild`）でクレンジング・検査してから、`<DIR>` に `addresses.bin` / `names.bin`（埋め込みと同じ KTS1 形式）、`manifest.json`（作成日時・出典・件数・フィンガープリント）、`NOTICE`（出典・gimei の MIT ライセンス表示）を出力する。クレンジング漏れなど検査に問題があれば書き出さない。書き出しは同じ親ディレクトリの一時ディレクトリにすべて書いてから各ファイルを rename で置き換えるため、途中で失敗しても中途半端な辞書は残らない（`<DIR>` 内の他のファイルには触れない）。出典がローカルファイルの場合はファイル名だけを記録する。
2. `--master-dir=<DIR>` または環境変数 `KATASHIRO_MASTER_DIR` を指定した場合のみその辞書を使う（自動では使わない）。`<DIR>` に `.bin` がなければ従来どおり `addresses.json` / `names.json` を読む。
3. 再現性: 生成結果は `seed`・`base-date`・辞書で決まる。チームで同じデータを使う場合は `<DIR>` を共有し、`katashiro master info` のフィンガープリント（`addresses.bin` と `names.bin` を連結した SHA-256）で一致を確認する。
4. 起動時間: 埋め込み辞書はゼロパースで 1ms 未満。外部辞書は `.bin` を読み込むだけ（パースなし）で、約 7.6MB の読み込み時間だけ増える。

# **3\. 実行モード（CLI & HTTPサーバー両対応）**

CLIフレームワークには外部依存を最小化するため、標準ライブラリの `flag.NewFlagSet` を採用する。

## **3.1 CLIモード仕様**

| サブコマンド | 主要オプション | 機能説明 |
| :---- | :---- | :---- |
| `next <N>` | `--format=[json|csv|jsonl]--profile=<name>--seed=<int64>--base-date=<YYYY-MM-DD>--loop--with-finance--with-kyc--with-profile--set key=value` | 現在のカーソル位置から重複なしで \$N\$ 件を払い出し、プロファイルのカーソルを進める。上限（1,000,000件）到達時はデフォルトでエラー終了（Exit Code 2）し、`--loop` 指定時のみカーソル 0 にラップアラウンドする。 |
| `export <N>` | `--out=<filepath>--format=[csv|json|jsonl|sqlite]--seed=<int64>--base-date=<YYYY-MM-DD>--force--offset=<M>--with-finance--with-kyc--with-profile--set key=value--set-raw key=value` | カーソル状態から独立してインデックス \$0 \\sim N-1\$ のデータを一括出力する（最大100万件対応）。テストごとに2,000件生成して使い捨てる場合は本コマンドを使用する。 |
| `reset` | `--profile=<name>` | 指定したプロファイルの払い出しカーソルを 0 に初期化する。 |
| `serve` | `--port=<number>--in-memory--seed=<int64>--base-date=<YYYY-MM-DD>` | E2Eテスト用のHTTP APIサーバーモードで起動する。デフォルトはファイル永続化カーソルと同期し、`--in-memory` 指定時はオンメモリのアトミックカウンタで動作する。 |

### **大量出力時のメモリ・スキーマ保護仕様**

* **ストリーミングJSON出力**: `--format=json` で100万件を出力する際も、全件スライスをメモリに保持せず、`[` 出力後に `bufio.Writer` で1件ずつエンコードしてストリーム出力し、OOM（Out of Memory）を完全に回避する。  
* **SQLite一括出力**: `modernc.org/sqlite`（CGO不要のPure Go）を採用。出力先ファイルが既に存在する場合は `--force` 指定時のみ `DROP TABLE IF EXISTS personas` で再作成し、単一トランザクション＋Prepared Statementで高速一括INSERTを行う。

## **3.2 HTTPサーバーモード（Docker / E2Eテスト向け）**

* `POST /api/v1/personas/next?count=10&profile=e2e&with_kyc=true&with_profile=true`  
  指定件数の重複なし個人データをJSON配列で返却する。上限到達時は `409 Conflict` を返す（`loop=true` 指定時はラップアラウンド）。  
* `POST /api/v1/personas/reset?profile=e2e`  
  該当プロファイルのカーソル位置を 0 にリセットする。

## **3.3 責務の切り分け・スコープ外事項 (Scope & Non-Goals)**

1. **検索・フィルタリング・クエリ機能の非提供**: 性別や年収範囲などによる条件検索は行わない。  
2. **カスタムフィールドDSLの非提供とスマートオーバーライド（v2で整理）**: 独自カラム追加のフック機構や独自DSLは持たない。属性の指定には `--set key=value`（例: `--set personal.gender=female`）または `jq` パイプ連携、テストコード側での上書きを使用する。  
3. **再現性の厳格化（v2で追加）**: `--base-date`（デフォルト固定値 `2026-01-01`、または明示的に `today` 指定で実行日）および `--seed`（デフォルト `1`）により、いつ・どの環境で実行しても1ビットの狂いもない完全な決定論的出力を保証する。  
4. **スマートオーバーライド（`--set key=value` による上流連動再計算）**: 単純な出力文字列の置換ではなく、境界値テストや地域・属性固定テストでデータ整合性が壊れないよう、`--set` を **「① 上流連動キー（Smart Override）」** と **「② 単純上書きキー（Post-Generation Override）」** の2段階で処理する。  
   1. **① 上流連動キー（関連フィールドを自動逆算・同期）**:  
      1. `personal.age=<N>`（例: `--set personal.age=20`）: 基準日（`--base-date`）時点でちょうど満 \$N\$ 歳となる365（366）日の生年月日レンジを逆算し、`seqID` ごとに異なる `personal.birthday` を決定論的に算出する。さらに下流の運転免許証取得年（18歳未満は `null`）や婚姻・扶養・職業（18歳未満は未婚・扶養0。2022年4月の民法改正で婚姻年齢は男女とも18歳）もその年齢に完全連動させる。  
      2. `personal.birthday=<YYYY-MM-DD>`（例: `--set personal.birthday=2006-01-01`）: 誕生日当日の年齢境界テスト等で使用。指定された生年月日から基準日時点の正確な `personal.age` を逆算し、下流モジュールも連動させる。  
      3. `personal.gender=<male|female|other|unspecified>`: 性別を固定する。`male` / `female` は使用する名（`first_name`）マスタも該当性別の辞書に切り替える。`other` / `unspecified`（「その他」「回答しない」の選択肢のテスト向け）は男女どちらの名マスタからも選ぶ。既定の生成では `male` / `female` のみを出す。  
      4. `contact.prefecture=<都道府県名>`（例: `--set contact.prefecture=福岡県`）: 住所マスタの都道府県別オフセットインデックスから該当都道府県のレコードのみを \$O(1)\$ で抽選し、郵便番号・市区町村・町域、および `--with-kyc` の運転免許証番号先頭2桁（都道府県公安委員会コード：福岡なら `90`）まで完全に整合させる。  
      5. `personal.last_name=<姓>` / `personal.first_name=<名>`（例: `--set personal.last_name=佐藤 --set personal.last_name_hiragana=さとう`、同姓同名テスト向け）: 漢字と読みを組で指定する。読みは `personal.{last,first}_name_hiragana` または `personal.{last,first}_name_katakana` のどちらかで必須（両方指定時は一致が必要）。読みからカタカナ・全銀協カナ・ローマ字（`romaji_name`・カード名義）を導出する。辞書は引かない（辞書の版による結果の違いを避けるため）。名前から性別は決めず、性別は通常どおり決定する（固定する場合は `personal.gender` を併用）。メールアドレスは `seqID` を含むため同姓同名でも一意のまま。  
      6. `kyc.document_type=<drivers_license|passport>`（`--with-kyc` 指定時、書類別テスト向け）: 本人確認に提示する書類の種類を固定する。`drivers_license` を指定した場合、生成対象に18歳未満が含まれる設定（`personal.age` / `personal.birthday` / `--min-age`）はエラーとする。
      7. `profile.is_married=<true|false>`（`--with-profile` 指定時）: 婚姻の有無を固定し、扶養人数をそれに連動させる（既婚: `0〜4`、未婚: 主に `0`）。`true` を指定した場合、生成対象に18歳未満が含まれる設定はエラーとする。
   2. **② 単純上書きキー（ブラックリスト名・特定文字列のテスト向け）**:  
      1. 上記以外のキー（例: `--set personal.full_name="山田 太郎"` や特定業種の固定など）は、レコード生成後の最終ステップで対象フィールドのみを上書きする（または呼び出し元のテストコード側で1行書き換える運用とする）。単純上書きでは読み仮名やローマ字の自動逆変換（形態素解析）は行わず、ツールの軽量性とシンプルさを維持する（読みまで揃えたい場合は ① の `personal.last_name` / `personal.first_name` を使う）。読みのキー（`personal.last_name_hiragana` 等）を漢字のキーと組にせず単独で指定した場合も単純上書きとして扱う。
   3. **③ 整合チェックなしの上書き（`--set-raw key=value`、異常系テスト向け）**: 利用者が意図して矛盾したデータ（例: 17歳で既婚、18歳で `profile.occupation=医師`・年収1500万円）を作り、利用側システムがそれを弾けるかを検証するために使う。すべてのキー（上流連動キーを含む）について、生成後の最終ステップで対象フィールドだけを上書きし、関連項目の再計算や組み合わせの検証は行わない。網羅的な異常系データの自動生成ではなく、利用者が指定した項目だけを崩す。
5. **分割生成（`export --offset=<M>`）**: インデックス \$M \sim M+N-1\$ を出力する。条件（`--set`）を変えて分割生成したデータを結合する場合に、`seqID` 由来の一意項目が重複しないようにする（`export` を `--offset` なしで複数回実行して結合すると、同じ `seqID` が重複する）。

# **4\. 100万件重複ゼロ保証のアルゴリズム設計（Cycle-Walking Feistel \+ SplitMix64）**

100万件のデータを事前生成して保持するのではなく、**要求された件数（例：2,000件）だけをリアルタイムに計算して合成する**。

## **4.1 なぜ「2,000件のテスト」で事前100万件生成が不要なのか**

* **辞書サイズと組み合わせ空間**: マスタデータは「姓」「名」「住所」の小さな辞書のみ（実データ辞書で姓約500件・名約1.3万件・住所約12万件、内蔵シードはさらに小さい）であり、生年月日（約23,000日）や番地・電話番号・口座番号などはすべて数値計算で動的に合成する。  
* **必要な生成件数**: 2,000件のテストデータをDBに入れて使い捨てる場合、生成するのは **2,000件だけ** でよい（実行時間は数ミリ秒）。全単射関数によって「1件目〜2,000件目」が絶対に衝突しないことが数学的に保証されているため、重複を避けるために余分な件数を生成してフィルタリングする必要は一切ない。

## **4.2 Cycle-Walking Feistel ネットワークによる全単射置換**

空間サイズ \$N \= 1,000,000\$ に対し、連番カーソル \$i \\in \[0, 999999\]\$ を一意の seqID \$\\in \[0, 999999\]\$ に写像する。  
通常のFeistelネットワークは \$2^{20} \= 1,048,576\$（10bit × 10bit）の空間で全単射となるため、出力に対して単純な剰余（`% 1000000`）をとると衝突が発生する。これを防ぐため、**Cycle-Walking（サイクルウォーキング）法**を採用する。

1. 入力 \$x \= i\$（\$0 \\le i \< 1,000,000\$）を 20bit（上位10bit \$L\_0\$, 下位10bit \$R\_0\$）に分割する。  
2. 4ラウンドのFeistel構造を適用する：  
   * \$L\_{r+1} \= R\_r\$  
   * \$R\_{r+1} \= L\_r \\oplus (F(R\_r, \\text{round}\_r, \\text{seed}) \\ & \\ \\text{0x3FF})\$  
3. 結合した20bit値 \$y \= (L\_4 \\ll 10\) \\mid R\_4\$ が \$y \\ge 1,000,000\$ の場合、\$x \= y\$ としてステップ2を再度適用する（\$y \< 1,000,000\$ になるまで繰り返す）。  
4. \$1,000,000 / 1,048,576 \\approx 95.37%\$ の確率で1回で収束し（平均反復1.05回）、\$0 \\sim 999,999\$ の範囲内で**衝突率0%の完全な全単射**が成立する。

## **4.3 SplitMix64 による属性間の相関排除**

算出された `seqID` から各属性（姓、名、住所、生年月日など）を導出する際、単純に `seqID % len(Master)` を使うと属性間で周期的な偏り（相関）が生じる。これを防ぐため、属性ごとに独立したソルト定数 `AttrSalt` を与え、`SplitMix64` ハッシュ関数で攪拌してからマスタ参照・数値算出を行う。

* `attrRand(seqID, salt) = splitMix64(uint64(seed) ^ (uint64(seqID) * 0x9E3779B97F4A7C15) ^ salt)`  
* 一意性が必須の項目（メールアドレス、口座番号、運転免許証交付番号、クレジットカード中間桁、パスポート番号、ダミー個人番号）にはハッシュ後の剰余を使わず、**`seqID`（0〜999,999）を直接埋め込むか、全単射変換した値を使用**し、100万件内の衝突ゼロを絶対保証する。

## **4.4 クロスプラットフォーム状態管理・排他制御**

* **保存パス解決**:  
  1. 環境変数 `KATASHIRO_STATE_DIR` があれば最優先。  
  2. `XDG_STATE_HOME` があれば `$XDG_STATE_HOME/katashiro`。  
  3. Unix系（Linux / macOS / WSL）は `~/.local/state/katashiro`、ネイティブWindowsは `os.UserConfigDir()/katashiro` にフォールバックする。  
* **排他制御**: OS間の `syscall.Flock` 差異を吸収するため `github.com/gofrs/flock`（またはOS別build tag実装）を用い、`cursor_<profile>.json` の読み書きをアトミックに保護する。
